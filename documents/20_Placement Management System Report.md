## ABSTRACT

The Training and Placement Cell (TPC) functions in most educational institutions remain manual, fragmented, and heavily reliant on distributed spreadsheets and paper records, resulting in significant administrative bottlenecks and tracking delays. The **Placement Management System (PMS)** is a highly automated web application engineered using the **PERN stack (PostgreSQL, Express, React, and Node.js)** that centralizes campus recruitment. The application implements a secure, compile-safe, and responsive architecture to establish a unified portal supporting **five core roles**: Students, Recruiters, Administrators, Mentors, and Alumni.

Key features include:
1. **Dynamic Eligibility Matching Engine:** Integrates a database-level query algorithm that cross-references student academic compliance metrics (CGPA, branch, active backlogs, gender preference) against active job criteria to generate personalized job feeds.
2. **Integrated Resume Builder:** Generates standardized, recruiter-ready PDF resumes directly from verified database fields to accelerate candidate screening.
3. **Multi-Stage Application Pipeline:** Provides real-time tracking of student applications through Socket.io WebSocket connections, allowing stage-by-stage pipeline advancement.
4. **Mentorship & Booking Scheduler:** Incorporates a mock interview coordination engine and mentorship booking module for students to schedule preparation sessions with mentors and alumni.
5. **Admin Command Center:** Offers deep system oversight including student/recruiter profile verification, document audit logs, system configuration parameters, and real-time server health statistics.

Enterprise-grade security is achieved through stateless JWT authentication in HTTP-only cookies, custom Double-Submit Cookie CSRF validation, Helmet-enforced security headers, Express-rate-limiting, and input sanitization middleware. The system has been validated via automated Jest integration tests, demonstrating robust, scalable performance ready for deployment and project defense.

## CHAPTER 1: INTRODUCTION

### 1.1 Overview
Campus recruitment coordinates corporate hiring drives with graduating students. For many years, this operation has been handled by Training and Placement Cells (TPC) manually or through fragmented folders and spreadsheets. These outdated mechanisms introduce data redundancy, human auditing errors, and massive administrative delays.

The **Placement Management System (PMS)** is an advanced full-stack web application designed to act as a secure, automated placement cell ecosystem. Implemented using the **PERN stack (PostgreSQL, Express, React, Node.js)**, the platform coordinates all hiring and training workflows. By implementing a cohesive role-based architecture, the platform connects **five primary user classes**:
* **Students:** Upload resumes, track drive deadlines, view eligible jobs, and coordinate preparation mock interviews.
* **Recruiters:** Post jobs, review eligible applicants, manage candidate stages, and upload verified offers.
* **Administrators:** Verify student profiles, approve recruiters, audit system access logs, and track overall analytics.
* **Alumni:** Upload referral jobs and share real-world interview preparation logs.
* **Mentors:** Conduct mock interviews and assign technical and HR readiness grades.

The system is designed with a premium, compile-safe **"Academic Authority"** interface utilizing React 19, TypeScript, and Tailwind CSS. It removes broken placeholders, providing a fully functional workflow optimized for student readiness and academic operations.

### 1.2 Problem Statement
Traditional placement coordination cells experience critical operational bottlenecks due to manual operations:
1. **Inefficient Data Verification:** Administrators spend hours manually cross-checking student academic sheets (CGPA, backlogs, branch) to verify job eligibility.
2. **Communication Silos:** Students miss drive application windows and remain uninformed about interview schedules because of a lack of instant notifications.
3. **Resume Inconsistency:** Recruiters screen hundreds of resumes with varying layouts, causing screening fatigue and overlooking potential matches.
4. **The Mentorship Gap:** Students have no direct channel within the placement workspace to get mock evaluations or tips from placed alumni.
5. **Security Risks:** Student and recruiter data remains vulnerable to unauthorized modification, parameter injection, and cross-site scripting (XSS) due to lack of standard security middlewares.

### 1.3 Objective
The primary objectives of the PMS are:
* **Digital Onboarding & Verification:** Automate student registration, profile completeness tracking, and document check-offs.
* **Automatic Resume Generator:** Implement an inline resume builder component mapping database fields onto clean A4 PDF prints.
* **Intelligent Filter Engine:** Implement backend database query matching to filter student feeds by job restrictions (minimum CGPA, branches, active backlogs, gender).
* **Real-time Pipeline Tracking:** Use WebSockets to deliver stage-by-stage status alerts (Applied, Shortlisted, Selected) to students instantly.
* **Alumni & Mentor Scheduling:** Enable calendar-driven mock interview reservations and technical evaluation grading.
* **Stateless Security Middleware:** Secure routes with JWT tokens, CSRF double-cookies, parameter sanitizers, and request validators.

### 1.4 Significance of PMS
* **Efficiency:** Reduces administrative drive screening time from days to seconds.
* **Transparency:** Eliminates tracking bias by showing candidates their active application stages.
* **Standardization:** Generates consistent resume outputs for recruiters, improving corporate evaluation rates.
* **Preparedness:** Provides a preparation pipeline through peer experience logs and mentor evaluation cycles.
* **Security:** Hardens student credentials against standard OWASP vulnerabilities.

## CHAPTER 2: BACKGROUND AND LITERATURE REVIEW

### 2.1 Background: Institutional Placement Cells & Workflows
Traditional Training and Placement Cells (TPC) operate as intermediaries between corporate HR departments and graduating student bodies. The recruitment pipeline follows a multi-step sequence:
1. **Job Notification:** Recruiters send job descriptions, CTC details, and eligibility criteria.
2. **Student Nomination:** Eligible students register their interest.
3. **Screening:** TPC coordinators manually verify CGPA, backlogs, and resumes.
4. **Evaluation:** Shortlisted students undergo online tests, technical interviews, and HR discussions.
5. **Placement Tracking:** Selected students receive offers, and TPC records selection databases.

Under manual systems, these steps are highly vulnerable to spreadsheet errors, delays, and tracking failures.

### 2.2 Related Work
Existing web platforms for placement cells have notable limitations:
* **Manual CRUD Portals:** Many basic campus portals only store student databases without automation tools.
* **Commercial Job Portals (LinkedIn, Indeed):** Generic platforms lack academic features, such as backlog limits, institutional credentials verification, and direct mock mentorship.
* **Inconsistent Resumes:** Third-party document tools generate highly variable layouts, slowing screening workflows.
* **Siloed Communication:** Separate apps (email, WhatsApp, drives) isolate communication, causing critical deadlines to be missed.

### 2.3 Existing Solutions
Table 2.1 compares manual workflows, commercial job portals, and the Placement Management System:

#### **Table 2.1: Comparison of Recruitment Processes**

| :--- | :--- | :--- | :--- |

| **Resume Handling** | Distributed email attachments | Unstandardized PDF uploads | Integrated Standardized A4 Resume Builder |
| **Real-time Tracking** | Batch emails / Physical notice boards | Static application status | Instant Socket.io event status updates |
| **Mentorship Integration** | Handled externally (Whatsapp/Calls) | No internal peer scheduling | Integrated Alumni & Mentor booking system |
| **Audit Trails** | No tracking of edits | System logs only | Persistent administrative database audit logs |

## CHAPTER 3: PROPOSED METHODOLOGY

### 3.1 Development Methodology
The project employs an **Agile Scrum development methodology**, organized into four distinct two-week sprints. This iterative approach ensures continuous feedback, incremental feature integration, and rapid testing cycles:
* **Sprint 1: Scope & Design System (Weeks 1-2):** Defined the SRS, drafted database relationships, and set up the "Academic Authority" design tokens.
* **Sprint 2: Architecture & Base APIs (Weeks 3-4):** Constructed backend routing, Express server structures, and Prisma PostgreSQL migrations.
* **Sprint 3: Role Portals & Frontend (Weeks 5-6):** Integrated student, recruiter, admin, and alumni views with real-time WebSocket messaging.
* **Sprint 4: Hardening & Testing (Weeks 7-8):** Implemented security middleware, resolved TypeScript build warnings, and executed Jest unit tests.

### 3.2 Development Environment Specifications
* **Machine Processor:** Intel Core i5 (12th Gen) / AMD Ryzen 5 or higher.
* **System RAM:** 8 GB DDR4 minimum.
* **Operating System:** Windows 11 / Linux (Ubuntu).
* **Database Engine:** PostgreSQL (Supabase Cloud Instance).
* **IDE:** Visual Studio Code.
* **Runtime:** Node.js v18+.
* **Version Control:** Git managed on GitHub.

### 3.3 System Overview (Components & Architecture)
The PMS uses a decoupled full-stack architecture:
* **Frontend:** Built with React 19 and TypeScript, using Vite as the build tool, Tailwind CSS for styling, and React Query for server state management.
* **Backend:** Node.js server powered by Express.js v5. It implements JWT role verification, validator schemas, and WebSocket listeners.
* **Data Layer:** PostgreSQL database managed through Prisma ORM to guarantee referential integrity and support cascade delete policies.
* **Auxiliary Services:** Cloudinary API for profile photo and document file storage; SMTP transporter for critical email digests.

## CHAPTER 4: FEATURES AND IMPLEMENTATION

### 4.1 User Authentication & Security Middleware
* **Stateless JWT Tokens:** Upon credentials validation, the backend issues an access token stored in an HTTP-only cookie.
* **Double-Submit Cookie CSRF:** Middleware validates that custom CSRF headers match tokens stored in cookies for all mutation requests.
* **Input Sanitization:** Uses `xss-clean` and `nosql-sanitizer` middleware to clean user inputs, preventing parameter injection and cross-site scripting.
* **Rate Limiting:** Protects endpoints from denial-of-service (DOS) attacks by restricting login attempts (5 per 15 minutes) and general API queries.

### 4.2 Student Profile & Resume Builder Engine
* **Profile Management:** Students maintain details including CGPA, active backlogs, passing year, skills, projects, and work history.
* **Standardized Resume Builder:** Converts structured JSON profiles into recruiter-ready A4 PDF resumes using jsPDF. This ensures consistent resume formatting, accelerating candidate screening.

### 4.3 Recruiter Job Feed & Smart Eligibility Filter
* **Job Posting Wizard:** Recruiters configure jobs with details like CTC, role requirements, minimum CGPA, maximum backlogs, branch constraints, and gender preferences.
* **Automatic Database Filtering:** When a student accesses the job feed, the query filters out listings where they do not meet the eligibility requirements.

```javascript
// Sample Backend Eligibility Checking logic
const getEligibleJobsForStudent = async (studentProfile) => {
  return await prisma.job.findMany({
    where: {
      status: 'open',
      minCGPA: { lte: studentProfile.cgpa },
      maxBacklogs: { gte: studentProfile.activeBacklogs },
      branches: { has: studentProfile.branch },
      targetCourses: { has: studentProfile.course },
      OR: [
        { genderPreference: 'all' },
        { genderPreference: studentProfile.gender }
      ]
    }
  });
};
```

### 4.4 Admin Dashboard, Verifications & Command Center
* **Mission Control:** Provides real-time statistics on total applicants, recruiter approvals, placement rates, and system audit trails.
* **Academic Verification:** Admins audit uploaded student sheets. Once verified, profiles are marked as verified, and readiness scores are updated.
* **System Controls:** Enables administrators to toggle registrations, restrict job postings, and archive student batches.

### 4.5 Mentorship Booking & Mock Interview Evaluation
* **Alumni portal:** Placed alumni share technical interview experiences and review requests.
* **Mock Scheduler:** Mentors schedule practice slots where students book sessions. Mentors record performance feedback across five grading metrics (technical knowledge, communication, system design, coding speed, and behavior).

### 4.6 Real-Time Socket.io Pipeline & Support Tickets
* **Real-time pipeline:** Delivers instant status updates (e.g. Applied to Shortlisted) to candidates.
* **Support Inbox:** Allows students and recruiters to submit support tickets, which are routed to the Admin team for review and response.
